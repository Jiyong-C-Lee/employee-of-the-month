# 시나리오 모드 v1 (선형 아크 + AI 브릿지) — 설계

2026-08-14. 피드백 1번(시나리오 모드)·반복플레이 한계 대응.

## 목표

- 사전 저작된 상황 비트를 **연대기 순서대로** 진행하는 시나리오 아크를 멀티 방 옵션으로 추가한다.
- 라운드 사이에 **보스의 회고 대사(브릿지)** 를 AI가 1~2문장 생성해, 직전 라운드 채택 발언을 다음 상황의 배경으로 엮는다. 플롯은 선형, 질감은 반응형.
- 조조 팩에 테마 아크 3종을 저작하고, 일반 랜덤 덱에도 상황을 증량한다(반복플레이 피드백).

## 비목표 (v1에서 안 함)

- 싱글 모드 변경 없음. 시나리오는 멀티 방 설정에서만 노출.
- 비트당 분기(approach 축 변형)는 v2. 스키마만 분기 수용 가능하게 설계해 둔다.
- 상황 자체의 AI 생성 없음 — free-tier 품질을 게임 콘텐츠의 핵심 경로에 두지 않는다.
- 나만의 보스(AI 생성 페르소나)에는 아크 미제공 (아크는 저작물이므로).

## 콘텐츠 스키마

`content/schema.ts`:

```ts
// situationSchema에 선택 필드 추가
{ text, question, id?: string, arcOnly?: boolean }
// id: 아크가 참조할 슬러그. arcOnly: true면 일반 랜덤 덱에서 제외.

// 신규 — 팩당 scenarios.json (선택 파일)
scenarioSchema = {
  id: string,          // "liubei" 등
  name: string,        // 방 설정 UI 표시명 ("숙적, 유비")
  tagline: string,     // 한 줄 소개
  beats: string[],     // situation id 순서 배열 (최소 4)
  finaleText: string,  // 마지막 비트 뒤 세션 종료 연출 문구 (endSession reason에 사용)
}
```

- 기존 18개 상황에 `id` 부여. 신규 상황은 성립 조건에 따라 `arcOnly` 표시.
- `packs.gen.ts`(gen-index.mjs)가 scenarios.json을 함께 묶는다. 없는 팩은 빈 배열.
- 로더 검증: beats의 모든 id가 해당 팩 situations에 존재해야 한다. 위반 시 로드 시점 throw.
- `listPersonas()`에 `scenarios: [{id, name, tagline, beatCount}]` 추가 (본문 제외 — 스포일러 방지).

## 엔진

`RoomState.config`에 `scenarioId?: string` 추가 (멀티 방 생성 시 선택).

- `beginRound`: scenarioId가 있으면 `situationOrder` 셔플 대신 아크 beats 순서로 상황을 뽑는다. 비트 소진 = `endSession(finaleText)` (기존 `endByExhaustion` 자리에 시나리오 전용 종료 분기).
- 라운드 상한(maxRounds)은 아크 길이로 대체 — 방 설정의 maxRounds는 시나리오 방에서 무시.
- 최고 직급 조기 등극(pendingChampion)은 그대로 둔다 — 아크 중간에 끝나도 성립하는 엔딩.
- `rematch`: 시나리오 방은 같은 아크를 처음부터 다시.

## AI 브릿지

`worker/ai/orchestrate.ts`에 `makeBridge` 추가 — `makeEpilogue`와 같은 골격(withFallback):

- 입력: persona, 직전 상황, 채택 발언(없으면 "채택 없음"), 다음 상황.
- 출력: 보스 1인칭 회고 대사 1~2문장. "자네 말대로 …했네. 그런데—" 톤. 다음 상황 본문과 겹치는 내용 재서술 금지(프롬프트로 제어).
- kind: `'bridge'` — 기존 관례로 `MODEL_BRIDGE` env 오버라이드가 자동 성립.
- **mock 폴백 = 브릿지 생략**(빈 문자열). 게임 진행에 영향 없음.
- 호출 시점: RESULT 단계에서 에필로그와 병렬로 미리 생성해 두고, 다음 라운드 `setPhase('SITUATION')` 페이로드에 실어 보낸다. 다음 라운드 시작을 LLM 대기로 막지 않기 위함.
  - 채택 없음 라운드도 브릿지는 생성한다("아무 안도 쓸 만한 게 없었지…" 톤).
  - DO 재기동으로 미리 생성분이 유실되면 브릿지 없이 진행(연출 레이어이므로 재생성 안 함).

## 전송·클라이언트

- `phase` 이벤트(SITUATION)에 `bridge?: string` 추가. 스냅샷 재구성 경로(`publicRoom`)에도 현재 라운드 브릿지 보존.
- 웹: 상황 컷(SituationCut) 위에 보스 말풍선으로 브릿지 렌더. 방 만들기(멀티)에 시나리오 선택 UI — "자유 상황(랜덤)" 대 아크 목록.

## 저작 계획 (조조 팩)

테마 아크 3종. 기존 상황 재사용 + 신규 저작(괄호가 신규, `arcOnly` 여부는 저작 시 판단):

1. **여포 아크** — "업계 최강 개발자의 명암". 여포 채용 → (여포의 첫 사고: 스톡옵션 요구) → (여포·유대표 이간질) → (하비 농성: 여포 구조조정 대치) → (최후: 여포의 재계약 읍소) — 비트 5.
2. **유비 아크** — "숙적인가 귀인인가". 유대표 의탁 → 관우 조건부 입사 → (청매실 회동: 술자리 떠보기) → (유대표 독립 조짐: 사내 스터디가 창업 모임으로) → 서서 영입안 → (적벽 전초: 유·오 연합 소문) — 비트 6.
3. **인재 영입전 아크** — "사람이 전부다". 채용공고(구현령) → 관우 조건부 → 허유 반말 사건 → 장송 훈수 → 서서 영입안 → (곽가 추모: 잃고 나서야 아는 것) — 비트 6.

일반 덱 증량: 아크 신규분 중 단독 성립하는 것은 `arcOnly` 없이 덱에도 편입 + 별도 단독 상황 신규 저작(목표: 덱 18 → 25+). 저작 문체·밀도는 기존 situations.json 기준(4~5문장, 기업 우화 톤, 질문 1개).

## 테스트

- content: 스키마·참조 무결성(beats id 존재), gen-index 산출 검증.
- worker: 시나리오 방 생성 → 비트 순서 고정 진행 → finale 종료 (mock AI 강제, 기존 room-do 테스트 골격 재사용). 브릿지 mock 폴백 시 빈 문자열 확인.
- 브릿지 실패가 라운드 진행을 막지 않는 것 (withFallback 계약).

## 리스크

- 브릿지 품질이 낮으면 "기억해주는 느낌"이 안 산다 → 프롬프트에 채택 발언 원문을 그대로 넣고, 재서술 금지·짧게 제한. 품질 미달 시 MODEL_BRIDGE로 판정 모델만 상향하는 탈출구.
- 아크 비트가 채택 결과와 무관하게 오는 것이 부자연스러운 케이스 → 비트 저작 시 "어떤 채택이든 뒤에 올 수 있는" 열린 도입부로 쓴다(저작 가이드).
